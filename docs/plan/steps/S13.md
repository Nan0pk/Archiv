# S13 — Index staleness: refresh on add, report N of M, incremental image index

**Phase B** (Stop the tool overclaiming) · depends on: S00

## Capability declaration

```yaml
name: index freshness on add
purpose: >
  Keep the image index and entity graph current whenever `archiv add` ingests new
  objects, and make `archiv images status` state the true relationship between what is
  indexed and what exists, instead of a bare count that can look confident while stale.
input_schema: >
  Newly ingested object digests and media types produced by `archiv add`; the durable
  object store's existing image-media rows for status reporting.
output_schema: >
  `archiv add` leaves the image index and entity graph reflecting every object it just
  ingested. `archiv images status` reports images indexed against total image objects in
  the store, never a bare "images indexed" count that hides a gap.
reads:
  - objects/**/meta.json
  - objects/**/original (image bytes, for embedding only)
  - derived/**/normalized/document.json (via the existing graph rebuild path)
writes:
  - index/images.sqlite3
  - index/entity_graph.sqlite3
forbidden_paths:
  - objects/**/original (write)
  - config/**
  - runs/**
network_policy: no network access
timeout_policy: bounded by the existing synchronous `add` command; no new retry loop
evidence_produced: rebuildable image-index and graph rows; an `images status` report
  that names both the indexed count and the total
validator:
  - tests/test_index_freshness.py::test_add_refreshes_the_image_index_and_graph
  - tests/test_index_freshness.py::test_status_reports_indexed_count_against_object_count
  - tests/test_index_freshness.py::test_image_index_update_is_incremental
```

## Why this step exists

Reproduced: after adding three images, `archiv images status` reported
`Image index ready: 4 images indexed` while the object store held seven image objects.
Searches silently missed the three newest files. `archiv add` refreshes the FTS index
automatically and reports counts; it does not touch the image index or the entity graph,
and nothing reports the divergence.

`rebuild_image_index` is also full-rebuild only — it re-embeds every image every time —
while the text path gained an incremental `update_search_index` in PR #117. Mirror that.

This is a correctness bug, not a polish item: a confident "ready" over a stale index is
exactly the class of thing this project exists not to do.

## Acceptance

The queue's existing targets are confirmed unchanged:

```
tests/test_index_freshness.py::test_add_refreshes_the_image_index_and_graph
tests/test_index_freshness.py::test_status_reports_indexed_count_against_object_count
tests/test_index_freshness.py::test_image_index_update_is_incremental
```

The first test must exercise `archiv add` on generated image and text fixtures and prove
both the image index and the entity graph reflect the newly added objects afterward — not
just the FTS index.

The second test must prove `archiv images status` reports the indexed count against the
true total number of image objects in the store, so a partial or stale index cannot read
as complete.

The third test must prove that updating the image index for newly added digests does not
re-run the image embedder against images that were already indexed — mirroring the
incremental text-index path added in PR #117, not `rebuild_image_index`'s full re-embed.

## Must not change

- Do not make `rebuild_image_index` or `archiv images rebuild-index` incremental by
  default; they stay explicit full rebuilds. Only the new `add`-triggered update path is
  incremental.
- Do not alter originals or canonical document evidence.
- Do not add a network call, a new required dependency, or a new model.
- Do not implement S14's doctor probes or README coverage test in this step.
