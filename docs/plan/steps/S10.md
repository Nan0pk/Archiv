# S10 — Rename image search to find-similar and delete the text embedder

**Phase B** (Stop the tool overclaiming) · depends on: S00

> **Stub expanded on 2026-09-06**, before implementing. What the stub predicted about the
> text query was right and is confirmed below. What it assumed about the image-to-image
> side was wrong, and the measurement that shows it is below too. Detail written months
> ahead of implementation is usually wrong; this is what that looks like in practice.

## Why this step exists

`archiv images search` presents a ranked table with four-decimal scores, but the
text side of the embedder is a nineteen-entry colour lookup table with a hash-scatter
fallback for every other word: `seed = sum(ord(c) * 31**i)`, then
`vec[(seed + k*13) % 128] += 0.5`. Reproduced on `d9a9b8d`: the query
`"a photo of a person smiling"` ranked an invoice first at 0.4296, in a corpus containing
no people, with no match floor to stop it.

The image-to-image side is fine. Perceptual near-duplicate detection over colour and
edge features is a real, useful capability — the same scan filed in four folders is a
genuine user problem. Keep that, drop the text query, and rename so the name matches
what it does.

The recall@1 test asserts >= 0.70 over ten solid-colour images queried by their own
colour names — the same names hardcoded in the lookup table. It measures the table
against itself and must be replaced by something meaningful or removed.

## Reproduced on `86a8b22`, before changing anything

A corpus of four generated images containing no people at all — one document-like page and
three flat colours:

| Query | Top result | Score |
|---|---|---|
| `a photo of a person smiling` | `invoice.png` | 0.4270 |
| `a cat wearing a hat` | `flat-slate.png` | 0.4666 |
| `xyzzy plugh frobnicate` | `invoice.png` | 0.3453 |
| *(empty string)* | all four returned | 0.0000 |

Three things this shows beyond what the stub recorded. Invented words score as confidently
as real ones, because the hash-scatter fallback gives every string a vector. A meaningless
query can outscore another meaningless query, so the ranking between queries is noise too.
And an **empty query returns the whole corpus** as ranked results, because a zero vector has
cosine zero against everything and the default floor is zero.

## The image-to-image side is not "fine", and that has to change the step

The paragraph above says perceptual near-duplicate detection is a real capability, and
[`../DECISIONS.md`](../DECISIONS.md) §6 keeps it on that basis. Measured, it works on some
content and not at all on the content this step uses to justify it.

Method: three groups of generated images, each group being one image filed four ways —
re-encoded as JPEG at quality 72, resized to half, brightened by 12%, and the original.
Cosine similarity within a group is a true near-duplicate pair; across groups is unrelated.

| Content | Lowest true match | Highest unrelated | Separated by |
|---|---|---|---|
| Colour-diverse images | 0.9994 | 0.9000 | **0.0994** |
| Document-like pages | 1.0000 | 1.0000 | **0.0000** |

On colour-diverse images the two populations are cleanly apart and a floor works. On
document-like pages every pair — matching or not — scores between 0.9993 and 1.0000, so no
floor can separate them. The 128-dimensional vector is dominated by global colour
statistics, and two light pages of black text have nearly identical colour statistics
whatever they say.

**So "the same scan filed in four folders", the problem this step names to justify keeping
the capability, is the one case it cannot solve.** It finds duplicate photographs. It
cannot tell two unrelated invoices apart.

That does not change what this step deletes — the text query goes either way. It changes
what may be claimed for what remains, and it means the match floor is necessary but not
sufficient: a floor stops nonsense scores being presented as matches, and does nothing
about a corpus where the scores carry no information. Sample size here is three groups of
four generated images, which is enough to show a 0.10 gap and a 0.00 gap apart, and not
enough to fix a floor to three decimal places.

## Capability declaration

```yaml
name: image-find-similar
purpose: Find images that are perceptually near-duplicates of a given image.
input_schema: a path to an image file on disk
output_schema: ImageSearchResult rows above a measured match floor, or none
reads: the image embedding index; canonical objects for the query image
writes: nothing
forbidden_paths: originals/**, derived/**
network_policy: none
timeout_policy: n/a
evidence_produced: the measured floor and the measurement behind it, in the test suite
validator: tests/test_image_similarity.py
```
