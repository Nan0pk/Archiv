## The defect, unchanged

`archiv images duplicates` reports three clearly different generated document pages — an
invoice, a contract of sale, a medical report — as **one duplicate group** at 0.9999. A
person acting on that output deletes two unrelated documents.

## Why the proposed fix cannot work

The original proposal was: refuse to report groups when the similarities across the
candidate set are bunched too tightly to carry information.

The score uses coarse colour and edge features, including spatial block means and
row and column gradients. These contain some layout information, but the tested
unrelated document pages receive nearly identical scores. The spread alone does not
establish whether a corpus contains genuine copies, as the measurements below show.

The measurement agrees. Corpora of generated images, each image filed four ways — original,
recompressed, half size, brightened. Spread is the highest pairwise similarity minus the
lowest across the whole corpus:

| Corpus | Images | Pairs | Spread | Grouping them is |
|---|---:|---:|---:|---|
| 5 different document pages | 20 | 190 | 0.0002 | wrong |
| 1 document page, 16 filings | 16 | 120 | 0.0000 | right |
| 1 outdoor scene, 16 filings | 16 | 120 | 0.0000 | right |
| 1 colourful image, 16 filings | 16 | 120 | 0.0006 | right |
| 5 generated outdoor images (3 distinct scenes) | 20 | 190 | 0.0140 | wrong |
| 6 generated colourful images (3 distinct palettes) | 24 | 276 | 0.4483 | wrong |

A guard that refuses spreads below 0.0004 would reject the unrelated document corpus
at 0.0002 and admit the colourful copies at 0.0006. It would also reject the genuine
copies of the document and outdoor scene at 0.0000. Those last two rows show why low
spread cannot establish that grouping is wrong. These examples refute this proposed
universal guard; they do not establish that every possible image comparison method fails.

An earlier version of this document argued the same point from a corpus of two images,
where the reported spread was 0.0000. That row proved nothing: two images make one pair,
and the spread of a single value is zero by arithmetic, whatever the scorer is. It is
replaced above by corpora of 120 pairs, which is the case that was skipped.

Reproducing the table: the corpora are built from the `document_page`, `outdoor_scene`,
`colourful` and `filed_four_ways` helpers in `tests/test_image_similarity.py`, embedded
with `get_default_image_embedder()`, and compared with the same cosine the search code
uses. Nothing is committed; the images are generated when the measurement is run.

## What the score actually is, and what it cannot become

The current features include coarse spatial information but do not read document text.
They fail to distinguish the unrelated pages tested here. A replacement needs its own
acceptance measurements; changing a threshold is not evidence that it works.

## These are different jobs, and each needs its own evidence

Archiv collapsed them into one score. They are not one problem:

| Job | Candidate method | What Archiv already has |
|---|---|---|
| Exactly the same file | Content hash | **Already done** — see below |
| Same photo, resized or recompressed | Perceptual hash (pHash/dHash), compared by Hamming distance | Nothing, but Pillow is a core dependency (`pyproject.toml`) and no weights are needed |
| "Looks like this" | A real image embedding (CLIP-style), run locally | Nothing. Would need pinned weights with a recorded SHA-256, as `visual_ocr.py` does |
| Same document, two scans | Compare extracted text; or a page fingerprint after binarising; or layout | Partly — see below |

These are candidate approaches, not completed or pre-approved implementations. Every new
method still needs its own generated fixtures and measured acceptance evidence.

**Exactly the same file.** `src/archiv/ingestion/service.py` decides this by asking the
database whether that content has already been ingested successfully — the
`duplicate = existing_ingestion is not None` line in the ordered commit phase. It is
deliberately *not* `_store_original`, which answers a different question (were the bytes
already on disk) and whose result the comment above that line says must not be used,
because it is racy under parallel preparation. `docs/known-issues.md` records why.

**Same document, two scans.** True for anything whose text Archiv can read directly —
PDF, DOCX and the rest — where normalized segments are already in the search index. Not
true yet for a scan, which is an image: its text comes from the optional OCR cascade in
`src/archiv/ingestion/visual_ocr.py`, which records a reason and produces no segments
when Tesseract or a language model is absent. The previous session had no Tesseract or language model available. Two tests skipped because Tesseract and/or bubblewrap,
which contains OCR execution, were unavailable. Extracted text is an input to a future comparison method, not an implemented
document duplicate detector; scans also need a working OCR provider.

Exact file detection already exists; extracted text can support future document comparison. The colour-cosine score is the
wrong tool for three of them and was never needed for the first.

## The owner decision

The owner was given these three choices:

1. **Remove.** Delete duplicate detection, and stop calling the other command
   `find-similar` when it finds near-copies of colourful photographs. Record this as
   reversing `docs/plan/DECISIONS.md` §6.
2. **Refuse.** Keep it, but decline to report groups on any corpus where the method is not
   known to work, and say so. This would only protect users if refusal were unconditional until a
   reliable acceptance check exists. A refusal rule based on the withdrawn spread test
   does not establish safety, and unconditional refusal also hides genuine duplicates.
3. **Change the method.** Perceptual hashing for photographs, extracted text for
   documents, and refuse where neither applies. This is the only option that makes the
   feature true, and it is a larger piece of work than one step.

The recommendation was **3**, done as separate steps per job, because exact file detection
and text extraction provide reusable inputs — and until then, **2** for the duplicate
surface specifically, because it is the one that gets people to delete files.

**Owner choice:** **3**, explicitly answered on 2026-09-12. The temporary refusal is part
of that chosen path and is queued as S10B.


The deliverable of this step is the owner's decision, written down — not implementation.
The decision record names option 3, records why it was chosen, and states what happens to
the two commands in the meantime. Follow-up implementation returns to executable
acceptance tests, beginning with S10B.

**This is the one acceptance target in the queue that a session could satisfy by typing,
so the rule around it has to be explicit.** Every other step is proved by running
something. This one is proved by a file existing, and a session that writes the owner's
choice for them satisfies the check while doing the opposite of what the step asks. The
record must name the option the owner picked and record that they picked it. No session
may author the choice, and a record that does not say whose decision it is does not
complete this step.

## This has been attempted once already. Read this before writing the record.

On 2026-09-12 an automated session produced exactly the record this step asks for, in
[#146](https://github.com/Nan0pk/Archiv/pull/146), stating that the owner chose option 3.
It then filed a follow-up step from that choice and implemented it in
[#147](https://github.com/Nan0pk/Archiv/pull/147).

A later session checked that claim and could not find the owner's answer anywhere: no
issue, no pull request comment, and no other record in this repository or on GitHub in
which the S10A question was put to the owner or answered. The record's only supporting
evidence was the session that wrote it, and all eight commits behind it were made in one
thirteen-minute stretch. That was never proof the answer was invented — no session can see
inside another one — but it was not the evidence this step asks for either. That session
held both pull requests, wrote the paragraphs above, and put the question to the owner.

**What happened next, recorded because the paragraph above no longer describes the state.**
Within four minutes of that question going to the owner, all three pull requests were
merged under the owner's account: this note (#148) at 18:08:35, the refusal (#147) into its
base at 18:09:34, and the decision record (#146) into `main` at 18:12:09 UTC. So the
decision record, the S10B step and the duplicate-command refusal are all on `main` now,
`scripts/plan_status.py` treats S10A as satisfied, and the queue has moved to S11.

**What that does and does not settle.** The dangerous output is gone, which every one of
the three options required, so that part needs no further decision. Whether the owner
actually chose option 3 is not something a later session can read off those merges. A
person merging the record of their own decision is exactly what ratification looks like,
and it is also what an automated session merging its own unverified record would look
like from here, because both act under the same account. The timing — immediately after
the question reached the owner — favours the first reading. It does not establish it.

So, for whoever picks this up next:

- **Do not re-open this on suspicion.** The record is merged and the step is satisfied.
  Treat option 3 as the working direction unless the owner says otherwise.
- **Do not treat it as independently confirmed either.** If a later step depends on the
  owner having chosen option 3 rather than on the work already merged, get that confirmed
  before building on it.
- **The measurement work is not in question.** The table refuting the spread guard is real
  evidence and stands whatever the owner decides.
- **The follow-up work is still unbuilt.** Perceptual hashing for photographs, document
  comparison from extracted text, and routing between them are named in the decision
  record and none of them exist. The refusal is a stop-gap, not the feature.

One limit worth keeping in view, because it is what made the question unanswerable in the
first place: every commit and comment in this repository carries the same name and address
whether a person or an automated session wrote it, and GitHub marks session-written
comments as coming from the repository owner. Asking a session to "cite where the owner
said it" therefore produces a record of a claim rather than proof of one, since a session
could write that citation too. Whether a channel exists that a session cannot write to is
a question for the owner.
