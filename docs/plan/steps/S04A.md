# S04A — Structured-output robustness, so a backend swap fails loudly instead of quietly

**Phase A** · depends on: S04

> Added after research, not in the original plan. It exists because the most common
> documented failure when swapping an LLM backend is not slowness or poor answers — it is
> structured output silently ceasing to be enforced, which then looks exactly like a
> quality regression and gets misdiagnosed for days.

## Why this step exists

Archiv's grounded answer is not prose. `build_grounding_prompt` (`grounding.py:20-79`)
demands a strict JSON object, and `parse_and_validate_grounded_response` (`:96-124`)
rejects anything that does not parse into `GroundedModelResponse`. So JSON adherence is
load-bearing: if it degrades, `ask` returns `partially_produced_but_invalid` and the user
sees a broken product.

Two documented failures make this concrete:

- **Ollama issue [#17933](https://github.com/ollama/ollama/issues/17933)** — structured
  output silently ignored on one backend. Schema-to-grammar conversion lives only in the
  llama.cpp library; the API layer accepted `format`, dispatched to a runner with no
  grammar hook, and generated unconstrained. It returned HTTP 200 even for an invalid
  schema. Measured: **61 of 65 outputs violated the schema**, and the reporter first
  misdiagnosed it as a model-quality problem.
- **[openclaw#114826](https://github.com/openclaw/openclaw/issues/114826)** — schema
  dialect mismatch. Unanchored regex patterns (`.*x.*`) that cloud providers accept are
  rejected by llama.cpp's grammar generator, which needs `^x$`. Tool calls then "fail
  silently or return malformed JSON".

Cloud models mostly paper over this by being good at instruction-following. A 7–8B local
model will not. Building the defence now — against the cloud backend, where it is easy to
test — means the machinery is already proven when the local model arrives.

## The evidence on constrained decoding is genuinely mixed — design for both readings

- **[JSONSchemaBench (arXiv:2501.10868)](https://arxiv.org/pdf/2501.10868)**, ~10,000 real
  schemas: constrained decoding can be *faster* (Guidance ~50% faster than unconstrained
  via fast-forwarding) and improved quality ~3% over LM-only. Useful failure taxonomy:
  **over-constrained** (rejects valid output) vs **under-constrained** (permits invalid
  output). It found XGrammar had the most under-constrained failures — silent invalidity.
- **[The Constraint Tax (arXiv:2605.26128)](https://arxiv.org/pdf/2605.26128)**, on small
  models: hard constrained decoding took validity from 61.5% to 100%, but answer accuracy
  from 19.7% down to 11.0%, and **wrong-but-schema-valid outputs rose from 49.5% to
  88.9%**.

The reconciliation: grammars buy validity, not correctness, and the smaller the model the
more they cost. So Archiv must count "invalid JSON" and "valid JSON that isn't supported
by the evidence" as **separate** signals. Collapsing them hides the second one.

## Capability declaration

```yaml
name: structured-output-enforcement
purpose: Make schema enforcement an explicit, declared backend capability, and convert
  silent schema failure into a loud, counted, bounded-retry outcome.
input_schema: GroundedModelResponse JSON schema
output_schema: GroundedModelResponse, or a recorded structured-output failure
reads: config/model.json
writes: runs/ask/<run_id>/*, runs/tasks/<id>/*
forbidden_paths: originals/**, derived/**
network_policy: inherited from the adapter
timeout_policy: inherited; the retry budget is bounded and counted
evidence_produced: per-run counters for schema_violation and valid_but_unsupported
validator: tests/test_structured_output.py
```

## What to build

1. **Declare the capability.** Each adapter states whether it can enforce a JSON schema.
   `ModelAdapter` (`model_adapter.py:54-57`) is currently a bare `complete()`; extend the
   protocol, defaulting to "cannot enforce" so a new backend is pessimistic by default.
2. **Fail loudly when it cannot.** If enforcement is unavailable, the run says so
   explicitly. Never degrade silently — that is the whole failure being prevented.
3. **Bounded retry with the validation error fed back.** On invalid JSON, retry a small,
   fixed number of times, including the specific validation error in the retry. Every
   attempt is counted and recorded in the run evidence. This lives in the **shared** path
   so `ask` and `report` both get it — remembering that `tasks.py:127-152` is a separate
   code path.
4. **Two separate counters.** `schema_violation` (did not parse or validate) and
   `valid_but_unsupported` (parsed fine, but cited nothing or cited outside the allowed
   set). The second already has a home: `parse_and_validate_grounded_response` rejects
   unknown citation ids at `grounding.py:116` and `:122`.

## Note for whoever does the eventual local swap

Record engine version, quantisation and model commit in the provenance block from S05/S06.
[LLMWare's benchmark](https://llmware.ai/resources/best-small-language-models-for-accuracy-and-enterprise-use-cases-benchmark-results)
found Llama-3 and 3.1 specifically degrade at `Q4_K_M` where other families hold up — so
quality must be re-measured *after* quantising, not before, and the quantisation level has
to be part of the record for that comparison to mean anything.
