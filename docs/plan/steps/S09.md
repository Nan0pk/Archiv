# S09 — Predict local runtime from cited hardware profiles

**Phase A** · depends on: S08 · **completes Phase A**

## Purpose

Answer the question that motivated all of Phase A: *"once I have the hardware, how slow
will this actually be?"* — with a number that carries an honest error band and a citable
source, and that becomes a measured fact the moment the hardware exists.

## The model

Inference latency splits into two regimes with different bottlenecks. Prompt processing
(prefill) reads the whole prompt at once and is compute-bound; token generation (decode)
produces one token at a time and is bound by memory bandwidth, because every generated
token requires reading the model's weights. So:

```
predicted_ask_ms ≈ retrieval_ms                       (local, model-independent, measured in S08)
                 + prompt_tokens     / prefill_tokens_per_second
                 + completion_tokens / decode_tokens_per_second
```

The two throughput constants are properties of the hardware and model, not of Archiv.
Before the hardware exists they come from published figures; afterwards they are measured
on the actual machine.

For a first estimate when no published figure matches the exact configuration, decode
throughput for single-stream generation is approximately

```
decode_tokens_per_second ≈ (memory_bandwidth_bytes_per_second / model_bytes) × MBU
```

where `model_bytes` is the **actual GGUF file size** — not parameter count × nominal bits,
which understates it — and MBU (Model Bandwidth Utilisation) is the achieved fraction of
peak bandwidth. Treat this as a bound on the range, not a point prediction.

**Use MBU ≈ 0.70 for consumer hardware in the 50–1000 GB/s band, with a 0.55–0.85 band.**
That figure is derived from published `llama.cpp` measurements against vendor bandwidth
specs and matches the practitioner consensus of 60–80% of theoretical ceiling. Two
non-obvious regularities to encode: **MBU falls as bandwidth rises** (fixed per-token
overheads do not shrink, so a 4-bit 8B model on a datacentre card achieves only ~35–45%),
and **MBU rises with model bytes** (the same GPU measured ~62% at Q4 and ~87% at F16).
Name the constant in code so it is auditable rather than buried.

## The finding that should change what you expect

**Archiv's workload is prefill-heavy, so on CPU the wait is before the first token, not
during generation.** An eight-passage evidence package plus the instruction block is
roughly 1,200–1,500 prompt tokens against only a few hundred output tokens. Published
practitioner figures put CPU prompt processing near 60 tok/s against roughly 2,500 tok/s
on a discrete GPU — a ~40× gap on the *prefill* term, far wider than the ~5–10× gap on
decode.

Concretely: the same question that returns in about a second on a GPU can spend tens of
seconds on a CPU-only machine *before it emits anything*. Do not model this with a single
"tokens per second" number — that is the mistake this step exists to avoid. Report the
prefill and decode terms separately, and show time-to-first-token, because on the
hardware most likely to be bought first it is the dominant term.

## Honest error band

Quote **±40%** on any single prediction. The dominant sources of variance are engine
choice (measured 1.4–1.7× between inference engines on identical hardware) and
quantisation variant — not the underlying physics, which is well behaved. Nominally
similar hardware can also invert: consumer desktop platforms are frequently capped by
interconnect bandwidth well below what the memory specification implies.

Build each prediction from **two independent anchors**: the bandwidth-derived ceiling
above, and the nearest-neighbour measured figure from a published benchmark table. Publish
both. **Where they disagree by more than 30%, that disagreement is the honest uncertainty**
— report it rather than averaging it away.

## What to build

**`docs/plan/hardware-profiles.json`** — a table of candidate model, quantisation and
hardware combinations. Every row must carry:

- the model, its parameter count and quantisation;
- the hardware, described specifically enough to be recognisable;
- `prefill_tokens_per_second` and `decode_tokens_per_second`, **as a range, not a point**;
- `source_url`, `retrieved_on`, and the harness that produced the figure;
- `confidence: "estimated" | "measured"`.

Populate it during this step from published measurements. This is a research task as much
as a coding one — the numbers are only as good as their sources, and a row without a URL
and a date is worthless. Report the spread honestly: throughput for the same model varies
substantially with quantisation, context length, thread count and thermal behaviour, and
a range that hides that is a false precision.

**Prediction output.** Given the S08 fingerprint and a chosen profile row, emit a
predicted median and a band. Label it `estimated`, name the profile row it came from, and
print the source URL alongside — so a reader can check the input rather than trusting the
output.

**`archiv model calibrate --local`.** Measures `prefill_tokens_per_second` and
`decode_tokens_per_second` on the actual machine and rewrites that row as `measured`.
From then on predictions for that machine are grounded, and the earlier estimate can be
compared against reality — which is itself worth recording, because it tells you how much
to trust the method next time.

## Rules

- An `estimated` figure may never be presented without its band and its source.
- A `measured` figure may never be presented without the machine it was measured on.
- If no profile row matches the user's hardware, say so and refuse to guess. A missing
  prediction is a better outcome than a fabricated one — the same principle
  `public-results.json` already applies with `"status": "externally_blocked"`.

## Acceptance

```
tests/test_model_calibration.py::test_every_hardware_profile_row_cites_a_source_and_a_date
tests/test_model_calibration.py::test_predictions_from_published_figures_are_labelled_estimated
tests/test_model_calibration.py::test_calibrate_local_overwrites_a_row_as_measured
tests/test_model_calibration.py::test_prediction_lands_within_the_stated_band_for_a_known_fingerprint
```

The last test uses a fixed fingerprint and a fixed throughput pair, so it checks the
arithmetic, not the world. Correctness of the *sources* is a review question, not a test
question — which is why every row must carry its URL.

## When this step merges

Phase A is complete: `archiv ask` and `archiv report` can be exercised without local
hardware, every remote-derived artefact is stamped, spend is bounded, and the eventual
local runtime is predicted with a stated error band. The drop-in path when hardware
arrives is:

```bash
archiv model configure --endpoint http://127.0.0.1:11434 --model <local-model>
archiv model calibrate --local
```
