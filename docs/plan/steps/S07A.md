# S07A — A refused run records why it was refused

**Phase A** · depends on: S07

> Filed from review rather than fixed in the change that found it, because it alters what
> a refused run leaves behind and deserves its own tests.

## The gap

The spend step's capability declaration promises "a per-run token and cost record in the
run evidence". An allowed run gets one. A refused run does not.

The check is the argument to the write:

```python
_write_json(evidence_dir / "cost.json", check_spend_allowance(prompt, layout.root).model_dump(...))
```

so when it raises, nothing is written. Confirmed: a ceiling-refused run leaves
`request.json`, `result.json` and `retrieval.json`, and no `cost.json`. The numbers that
caused the refusal reach the person through the error message and are then gone.

That is the wrong way round. A refusal is the run most worth having evidence for: it is
the one where somebody will later ask what the ceiling was, what had been spent, and
whether a projection existed at all.

## What to change

- Compute the pre-flight result, write it, then act on it — rather than writing the
  result of a call that may raise.
- The same applies to the report path, which reaches the ceiling through the same adapter
  and writes its own run evidence separately.
- Decide what a refused run's `result.json` should carry. `blocked_by_policy` already
  exists and is what the evaluation-marker refusal uses; a spend refusal is the same
  shape and should probably not arrive as a generic failure.
